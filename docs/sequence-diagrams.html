Diagramas de Secuencia

Casos de uso — Vue 3 · Spring Boot (Java 25) · PostgreSQL · JWT

UC-A1

Login

El usuario ingresa sus credenciales. El backend verifica la contraseña con BCrypt y, si son válidas, emite un access JWT (en cuerpo) y un refresh token opaco (en cookie HttpOnly).

Auth 
sequenceDiagram
    actor U as Usuario
    participant L as LoginView
    participant SA as stores/auth
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    U->>L: usuario + contraseña
    L->>SA: login(user, pass)
    SA->>H: POST /api/auth/login (auth:false)
    H->>B: POST /api/auth/login
    B->>DB: SELECT app_user WHERE username=?
    DB-->>B: AppUser + password_hash
    B->>B: BCrypt.verify(pass, hash)
    alt Credenciales válidas y usuario habilitado
        B-->>H: 200 AuthResponse + Set-Cookie rentals_refresh (HttpOnly)
        H-->>SA: { accessToken, expiresIn, user{id, role, tenantId} }
        SA->>SA: accessToken en memoria — status = authenticated
        SA-->>L: rol detectado
        L-->>U: AdminView ó TenantView según rol
    else Credenciales inválidas o usuario deshabilitado
        B-->>H: 401 ProblemDetail (mismo texto siempre)
        H-->>SA: ApiError(401)
        SA-->>L: error
        L-->>U: "Usuario o contraseña incorrectos"
    end
UC-A2

Restaurar sesión tras recarga

Al recargar la página el access token se pierde de memoria. App.vue llama a restoreSession(), que usa la cookie HttpOnly para obtener un token nuevo sin pedir credenciales de nuevo.

Auth 
sequenceDiagram
    actor U as Usuario
    participant A as App.vue
    participant SA as stores/auth
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    U->>A: Recarga la página
    A->>SA: restoreSession()
    SA->>H: POST /api/auth/refresh (auth:false)
    Note over H,B: Cookie HttpOnly enviada automáticamente por el navegador
    H->>B: POST /api/auth/refresh
    B->>DB: SELECT refresh_token WHERE token_hash = SHA256(cookie)
    alt Token válido, no revocado y usuario habilitado
        DB-->>B: RefreshToken activo
        B->>DB: UPDATE refresh_token SET revoked_at = now (revoca el anterior)
        B->>DB: INSERT nuevo refresh_token (rotación)
        B-->>H: 200 AuthResponse + nueva Cookie (rotación)
        H-->>SA: accessToken + user
        SA->>SA: status = authenticated
        SA-->>A: rol del usuario
        A-->>U: AdminView ó TenantView
    else Token expirado, revocado o usuario deshabilitado
        B-->>H: 401 + Set-Cookie borra rentals_refresh
        H-->>SA: ApiError(401)
        SA->>SA: status = anonymous
        SA-->>A: anonymous
        A-->>U: LoginView
    end
El refresh token se rota en cada uso: el anterior queda revocado, se emite uno nuevo. Si llega un token ya revocado (posible robo), se revocan TODAS las sesiones del usuario.
UC-A3

Renovación automática de token

Si una petición recibe 401 (access token expirado), http.js renueva el token de forma transparente y reintenta la petición original una sola vez. Refrescos concurrentes comparten una única Promise.

Auth 
sequenceDiagram
    participant C as Componente Vue
    participant ST as stores/tenants
    participant H as http.js
    participant SA as stores/auth
    participant B as Backend

    C->>ST: acción (p.ej. loadTenant)
    ST->>H: GET /api/tenants/1 (Bearer expirado)
    H->>B: GET /api/tenants/1
    B-->>H: 401 Unauthorized
    H->>SA: refreshAccessToken()
    Note over SA,B: Refrescos concurrentes reutilizan la misma Promise
    SA->>B: POST /api/auth/refresh (cookie HttpOnly)
    alt Refresh exitoso
        B-->>SA: 200 nuevo accessToken
        SA->>SA: accessToken actualizado en memoria
        SA-->>H: token renovado
        H->>B: GET /api/tenants/1 (Bearer nuevo — solo un reintento)
        B-->>H: 200 TenantDetailDto
        H-->>ST: datos
        ST-->>C: estado actualizado — transparente para el usuario
    else Cookie expirada o revocada
        B-->>SA: 401
        SA->>SA: clearSession() + tenantsStore.reset()
        SA-->>H: onAuthFailure()
        H-->>ST: ApiError(401)
        ST-->>C: error
        C-->>C: App.vue muestra LoginView
    end
UC-A4

Logout

El backend revoca el refresh token activo y borra la cookie. El store limpia el access token de la memoria y resetea el estado de la aplicación.

Auth 
sequenceDiagram
    actor U as Usuario
    participant AH as AppHeader
    participant SA as stores/auth
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    U->>AH: Clic "Salir"
    AH->>SA: logout()
    SA->>H: POST /api/auth/logout (auth:false)
    Note over H,B: Cookie HttpOnly enviada automáticamente
    H->>B: POST /api/auth/logout
    B->>DB: UPDATE refresh_token SET revoked_at = now (si existe)
    B-->>H: 204 + Set-Cookie borra rentals_refresh (idempotente)
    H-->>SA: ok
    SA->>SA: clearSession() — accessToken = null, status = anonymous
    SA->>SA: tenantsStore.reset()
    SA-->>AH: sesión cerrada
    AH-->>U: LoginView
UC-A5

Cambio de contraseña

Al cambiar la contraseña el backend revoca todas las sesiones activas del usuario. El frontend cierra la sesión actual y redirige al login, incluyendo otros dispositivos abiertos.

Auth 
sequenceDiagram
    actor U as Usuario
    participant CP as ChangePasswordForm
    participant SA as stores/auth
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    U->>CP: contraseña actual + nueva contraseña
    CP->>SA: changePassword(current, newPass)
    SA->>H: PUT /api/auth/password (Bearer)
    H->>B: PUT /api/auth/password
    B->>B: BCrypt.verify(currentPassword, hash)
    alt Contraseña actual correcta y nueva contraseña válida
        B->>DB: UPDATE app_user SET password_hash = BCrypt(newPass)
        B->>DB: UPDATE refresh_token SET revoked_at = now (TODAS las sesiones)
        B-->>H: 204 + Set-Cookie borra rentals_refresh
        H-->>SA: ok
        SA->>SA: clearSession()
        SA-->>CP: ok
        CP-->>U: "Contraseña cambiada. Inicia sesión de nuevo"
        CP-->>U: App.vue muestra LoginView
    else Contraseña actual incorrecta
        B-->>H: 401 ProblemDetail
        H-->>SA: ApiError(401)
        SA-->>CP: error
        CP-->>U: "Contraseña actual incorrecta"
    else Nueva contraseña inválida (menos de 10 caracteres)
        B-->>H: 400 ProblemDetail + campo errors
        H-->>SA: ApiError(400)
        SA-->>CP: error de validación
        CP-->>U: Error de validación
    end
Revocar TODAS las sesiones activas es intencional: si el usuario cambia la contraseña por sospecha de compromiso, cierra también los accesos desde otros dispositivos.
UC-AD1

Registrar arrendatario — RF-01

El administrador completa el formulario con los datos del arrendatario y sus credenciales iniciales. Tenant y AppUser se crean en una única transacción atómica: si el username ya existe, nada se persiste.

Admin 
sequenceDiagram
    actor A as Administrador
    participant TF as TenantForm
    participant ST as stores/tenants
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    A->>TF: nombre, unidad, contacto, día de pago, fecha inicio, monto mensual, username, contraseña inicial
    TF->>ST: createTenant(request)
    ST->>H: POST /api/tenants (Bearer ADMIN)
    H->>B: POST /api/tenants
    B->>B: @Valid CreateTenantRequest
    B->>DB: BEGIN TRANSACTION
    B->>DB: INSERT INTO tenant (full_name, unit, ...)
    B->>DB: SELECT app_user WHERE username = ? (verifica unicidad)
    alt Username disponible
        B->>DB: INSERT INTO app_user (role=ARRENDATARIO, password_hash=BCrypt(pass))
        B->>DB: COMMIT
        B->>B: DebtCalculatorService.calculate(tenant, now)
        B-->>H: 201 TenantDetailDto + Location header
        H-->>ST: TenantDetailDto
        ST->>ST: Añade resumen a la lista local
        ST-->>TF: ok
        TF-->>A: Arrendatario registrado
    else Username ya existe
        B->>DB: ROLLBACK (ni tenant ni usuario creados)
        B-->>H: 409 ProblemDetail
        H-->>ST: ApiError(409)
        ST-->>TF: error
        TF-->>A: "El nombre de usuario ya está en uso"
    end
La garantía (si se informa en el mismo formulario) se crea en una segunda llamada independiente al endpoint de cargos únicos (UC-AD3), igual que en v1.
UC-AD2

Marcar mes como pagado — RF-04

El administrador marca un mes adeudado como pagado. La operación es idempotente (ON CONFLICT DO NOTHING). El backend recalcula la deuda y devuelve el TenantDetailDto actualizado.

Admin 
sequenceDiagram
    actor A as Administrador
    participant MT as MonthsTable
    participant ST as stores/tenants
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    A->>MT: Clic "Marcar pagado" en el mes 2026-09
    MT->>ST: markMonthPaid(tenantId, "2026-09")
    ST->>H: PUT /api/tenants/1/paid-months/2026-09 (Bearer ADMIN)
    H->>B: PUT /api/tenants/1/paid-months/2026-09
    Note over B: Idempotente — ON CONFLICT DO NOTHING
    B->>DB: INSERT INTO paid_month (1, '2026-09') ON CONFLICT DO NOTHING
    B->>DB: SELECT tenant con paid_months y one_time_charges
    B->>B: DebtCalculatorService.calculate(tenant, now)
    B-->>H: 200 TenantDetailDto (deuda recalculada)
    H-->>ST: TenantDetailDto
    ST->>ST: detailsById[1] = TenantDetailDto
    ST-->>MT: estado reactivo actualizado
    MT-->>A: Mes desaparece de la lista de adeudados
UC-AD3

Registrar cargo único — RF-02

El administrador agrega un cargo irregular (garantía, reparación, etc.) a un arrendatario. El cargo suma al total adeudado hasta que sea marcado como pagado.

Admin 
sequenceDiagram
    actor A as Administrador
    participant CF as ChargeForm
    participant ST as stores/tenants
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    A->>CF: descripción + monto (USD)
    CF->>ST: addCharge(tenantId, { description, amount })
    ST->>H: POST /api/tenants/1/charges (Bearer ADMIN)
    H->>B: POST /api/tenants/1/charges
    B->>B: @Valid CreateChargeRequest
    B->>DB: INSERT INTO one_time_charge (tenant_id, description, amount, paid=false)
    B->>DB: SELECT tenant + paid_months + one_time_charges
    B->>B: DebtCalculatorService.calculate(tenant, now)
    B-->>H: 201 TenantDetailDto
    H-->>ST: TenantDetailDto
    ST->>ST: detailsById[1] = TenantDetailDto
    ST-->>CF: ok
    CF-->>A: Cargo aparece en la lista y suma al total adeudado
UC-AD4

Marcar cargo único como pagado

El administrador registra el cobro de un cargo único. Idempotente: si ya estaba pagado, devuelve igualmente el estado actualizado. El total adeudado se recalcula en el backend.

Admin 
sequenceDiagram
    actor A as Administrador
    participant TD as TenantDetail
    participant ST as stores/tenants
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    A->>TD: Clic "Marcar pagado" sobre el cargo #10
    TD->>ST: markChargePaid(tenantId, chargeId)
    ST->>H: PUT /api/tenants/1/charges/10/paid (Bearer ADMIN)
    H->>B: PUT /api/tenants/1/charges/10/paid
    Note over B: Idempotente — guarda paid=true aunque ya lo estuviera
    B->>DB: UPDATE one_time_charge SET paid=true WHERE id=10 AND tenant_id=1
    B->>DB: SELECT tenant + paid_months + one_time_charges
    B->>B: DebtCalculatorService.calculate(tenant, now)
    B-->>H: 200 TenantDetailDto (deuda recalculada)
    H-->>ST: TenantDetailDto
    ST->>ST: detailsById[1] = TenantDetailDto
    ST-->>TD: estado reactivo actualizado
    TD-->>A: Cargo marcado como pagado y descontado del total
UC-T1

Ver estado de cuenta propio — RF-05

El arrendatario ve su cuenta al iniciar sesión. El endpoint extrae el tenantId directamente del JWT, eliminando el riesgo de acceder a la cuenta de otro arrendatario cambiando un parámetro (IDOR).

Arrendatario 
sequenceDiagram
    actor T as Arrendatario
    participant TV as TenantView
    participant ST as stores/tenants
    participant H as http.js
    participant B as Backend
    participant DB as PostgreSQL

    T->>TV: App.vue carga TenantView (rol = ARRENDATARIO)
    TV->>ST: loadMyAccount()
    ST->>H: GET /api/me/tenant (Bearer ARRENDATARIO)
    H->>B: GET /api/me/tenant
    Note over B: tenantId extraído del JWT — sin parámetro en URL (previene IDOR)
    B->>DB: SELECT tenant WHERE id = tenantId (del JWT)
    B->>DB: SELECT paid_months + one_time_charges WHERE tenant_id = tenantId
    B->>B: DebtCalculatorService.calculate(tenant, now)
    B-->>H: 200 TenantDetailDto
    H-->>ST: TenantDetailDto
    ST->>ST: myAccount = TenantDetailDto
    ST-->>TV: estado reactivo
    TV-->>T: Meses adeudados + total USD + badge AL_DIA / ATRASADO
Si el arrendatario intentara llamar a GET /api/tenants o GET /api/tenants/{id} recibiría 403, ya que esas rutas requieren rol ADMIN.
