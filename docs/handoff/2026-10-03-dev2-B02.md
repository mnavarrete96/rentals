## Decisiones tomadas y por qué

### D-1: paidMonths como @ElementCollection (no entidad PaidMonth con embedded PK)
La ARCHITECTURE §5.3 especifica `@ElementCollection Set<YearMonth>`. La tarea del líder describía `PaidMonth`
como entidad con `PaidMonthId` y campo `paidAt`, pero eso contradice:
- ADR-006: el estado/historial calculado no se persiste (y `paidAt` no está en el esquema de ARCHITECTURE §5.1)
- §5.3: "Es un valor, no una entidad: no necesita id propio"
- §3: `repository/` lista solo `TenantRepository, OneTimeChargeRepository, AppUserRepository, RefreshTokenRepository` — sin `PaidMonthRepository`

Decisión: seguir la ARCHITECTURE. Se reporta al líder en esta nota para que actualice la descripción de B-02 si cambia la decisión.

### D-2: Sin columna `status` en `tenant`
La tarea del líder incluía columna `status tenant_status` en la tabla `tenant`. La ARCHITECTURE §5.1 NO tiene esa columna y ADR-006 prohíbe persistir campos calculados. El status lo computa `DebtCalculatorService`.

### D-3: SQL siguiendo ARCHITECTURE §5.1 (no el SQL de la tarea)
El SQL de la tarea usaba `BIGSERIAL`, `ON DELETE RESTRICT`, sin `CHECK` en year_month, `contact` nullable y `monthly_amount > 0`. ARCHITECTURE §5.1 define `BIGINT GENERATED ALWAYS AS IDENTITY`, `ON DELETE CASCADE`, check de formato, `contact NOT NULL` y `monthly_amount >= 0`. Se siguió la ARCHITECTURE.

### D-4: Spring Boot 4.x — cambios de packages en tests
En Spring Boot 4.x, los test slices se distribuyeron en módulos separados y los packages cambiaron:
- `@DataJpaTest` → `org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest` (módulo: `spring-boot-starter-data-jpa-test`)
- `@AutoConfigureTestDatabase` → `org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase` (módulo: `spring-boot-jdbc-test`, incluido via `spring-boot-starter-data-jpa-test`)
- Testcontainers 2.0.5 (usado por SB 4.1.0): los artefactos renombraron a `testcontainers-junit-jupiter` y `testcontainers-postgresql` (con prefijo `testcontainers-`)

Estos cambios afectan a B-03, B-04, B-06 si usan slice tests.

## Problemas conocidos / riesgos
- `ddl-auto=create-drop` en tests no valida que el Flyway SQL sea compatible con la estructura JPA. Un test de integración con `@SpringBootTest` + Flyway + Testcontainers validaría esto end-to-end. Recomendado para B-06 o B-04.
- El `Hibernate: drop table... cascade` falla en log al shutdown (container PostgreSQL ya terminó). Es inofensivo — los tests pasaron. No requiere acción.
- La decisión de paidMonths como @ElementCollection debe ser coordinada con el líder y el architect antes de B-04 (los controllers dependen de cómo se manipulan los meses pagados).
