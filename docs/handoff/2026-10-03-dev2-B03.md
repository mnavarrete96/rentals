## Decisiones tomadas y por qué

### D-1: Firma `calculate(Tenant, YearMonth)` — no `(Tenant, LocalDate)` con check de paymentDay
La tarea del líder pedía `LocalDate asOf` y una regla: "el mes actual es adeudado si `asOf.dayOfMonth >= paymentDay`".
La ARCHITECTURE §4.3 especifica:
- firma: `calculate(Tenant tenant, YearMonth currentMonth)`
- "`paymentDay` sigue sin afectar al conteo (igual que v1). Cambiar eso sería un cambio de regla de negocio y requiere actualizar el SPEC primero."
calc.js tampoco verifica paymentDay — usa directamente el mes de `today`.
Decisión: seguir ARCHITECTURE. Se reporta al líder para que decida si el paymentDay check es un cambio de SPEC aprobado.

### D-2: `DebtSummary` en `service/` (no `service/dto/`)
ARCHITECTURE §3 lista `DebtSummary (record)` directamente bajo `service/`. No existe ninguna mención a `service/dto/` en la arquitectura. El paquete `web/dto/` es para DTOs de la capa HTTP; `DebtSummary` es interno al service y no se expone directamente vía HTTP (el mapper lo convierte).
La tarea del líder pedía `service/dto/DebtSummary.java` pero la ARCHITECTURE es el documento autoritativo.

### D-3: Seed con DO $$ ... RETURNING id
`BIGINT GENERATED ALWAYS AS IDENTITY` no permite INSERT con id explícito sin `OVERRIDING SYSTEM VALUE`.
Usar `RETURNING id INTO variable` es la forma idiomática en PL/pgSQL. Evita asumir que la secuencia arranca en 1.

## Problemas conocidos / riesgos
- **paymentDay check**: si el líder confirma que sí se quiere ese check (localDate + paymentDay), la firma del método y el SPEC deben actualizarse antes de que B-04 consuma `DebtCalculatorService`. Impacto bajo (solo cambia la firma y la lógica del cursor).
- **`service/dto/`**: si el architect decide introducir ese paquete para mantener DTOs de servicio separados, `DebtSummary` se mueve sin romper nada (cambia solo el import en el mapper y el service).
- El test de cruce de año verifica orden ascendente. El algoritmo usa `cursor.plusMonths(1)` que preserva el orden natural de YearMonth.
